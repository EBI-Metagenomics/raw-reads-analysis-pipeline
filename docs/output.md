# MGnify v6 raw-reads-analysis-pipeline output documentation

This document describes the different outputs produced by the MGnify v6 raw-reads-analysis-pipeline, which analyses whole genome sequencing (WGS) raw reads to generate taxonomic and functional profiles using closed-reference databases.

The pipeline functions on a per-run/sample basis, and so the outputs directory structure is also organised on a per-run basis. Additionally, the pipeline generates top-level summary files which are aggregated from all the import runs.

In this documentation, the different contents of both per-run and top-level summary outputs will be described.

## Per-run output files

There are three general categories of results, each with their own output directory. Each successful run should have all five of these directores:

```
├── qc
├── taxonomy-summary
└── function-summary
```

Since these results are per-run, many of the output files use the run ID as a prefix. For the purposes of this documentation we will use the run ID `ERZ12345`.

### `qc`

The `qc` directory contains output files related to the quality control (QC) and decontamination steps of the pipeline. A `fastp` report is generated for QC and after decontamination, and these are combined in a `multiqc` report. The `fastp` reports are `json` files containing a summary of the `fastp` run, including the number of reads and/or bases that were filtered for various reasons.

```
qc
├── ERZ12345_qc.json
├── ERZ12345_decontamination.json
└── ERZ12345_multiqc_report.html
```

### `taxonomy-summary`

The `taxonomy-summary` directory contains files related to taxonomic profiling of the run. It contains three subdirectories each corresponding to a taxonomic profiling method:
* **`motus`**: generated by mOTUs3
* **`silva-lsu`**: generated by `infernal cmsearch` extraction of rRNA sequences followed by `mapseq` mapping to a `silva` rRNA LSU reference database.
* **`silva-ssu`** similar to above but mapped to a rRNA SSU (i.e. 16S) reference database

Each subdirectory contains:
1. a standardised text file reporting read counts of each taxa
2. an interactive Krona plot

Output files:
* **`ERZ12345_motus.txt.gz`**: This text file contains a tab-separated table of read counts for each taxa detected, at various taxonomic levels. It is also the Krona text input that is used to generate the Krona HTML file.
* **`ERZ12345_motus.html`**: This `html` file contains the Krona HTML file that interactively displays the distribution of the different taxonomic assignments.
* **`ERZ12345_silva-lsu.txt.gz`**: This text file contains a tab-separated table of read counts for each taxa detected, at various taxonomic levels. It is also the Krona text input that is used to generate the Krona HTML file.
* **`ERZ12345_silva-lsu.html`**: This `html` file contains the Krona HTML file that interactively displays the distribution of the different taxonomic assignments.
* **`ERZ12345_silva-ssu.txt.gz`**: This text file contains a tab-separated table of read counts for each taxa detected, at various taxonomic levels. It is also the Krona text input that is used to generate the Krona HTML file.
* **`ERZ12345_silva-ssu.html`**: This `html` file contains the Krona HTML file that interactively displays the distribution of the different taxonomic assignments.

```
taxonomy-summary
├── motus
│   ├── ERZ12345_motus.txt.gz
│   └── ERZ12345_motus.html
├── silva-lsu
│   ├── ERZ12345_silva-lsu.txt.gz
│   └── ERZ12345_silva-lsu.html
└── silva-ssu
    ├── ERZ12345_silva-ssu.txt.gz
    └── ERZ12345_silva-ssu.html
```

### `function-summary`

The `function-summary` directory contains files related to functional profiling of the run. It contains one subdirectory, `Pfam-A`, corresponding to the one functional profiling method implemented based on `hmmsearch` mapping to the `Pfam-A` reference database.

Output files:
*	**`ERZ12345_pfam.txt.gz`**: This text file contains a tab-separated table of read counts for each detected Pfam-A profile (or “function”).
*	**`ERZ12345_pfam.stats.json`**: This `json` file contains a summary of the numebr of reads mapped to Pfam, the number of Pfam models with hits and a sum of the number of hits across all Pfam models.
*	**`ERZ12345_pfam_orf_filter.stats.json`**: Only with `pfam_orf_filter`. ORFs and residues before and after the filter, reads with and without a gene call, and whether the filter kept all ORFs because too few reads had a call.
*	**`ERZ12345_pfam_alignments.parquet`**: Only with `pfam_search_engine = nail` or `kfpfam`, unless `pfam_alignments` is `false`. One row per domain that passes Pfam's gathering thresholds, and with `pfam_weak_evalue` weaker ones too, written with zstd and sorted by family then read, which costs about 60 bytes a domain, so tens of MB for a run at the 2 M-read cap. Columns:

| Column | What |
|---|---|
| `read` | read name, as the merged FASTA has it |
| `frame`, `orf_begin`, `orf_end` | the translated stretch this domain sits on |
| `read_from`, `read_to` | the aligned residues' nucleotides on the read, 1-based inclusive, forward numbering, so no frame arithmetic is needed to place a domain on its read |
| `pfam`, `pfam_version`, `domain` | Pfam accession and its version, as columns only mean something for one version of a model, and which reported domain this is for that (read, family); those under the gathering thresholds are numbered after those above |
| `above_ga` | whether the domain passes the gathering thresholds. Always true without `pfam_weak_evalue`; **with it, filter on this for the hits the profile counts** |
| `seq_score`, `dom_score`, `seq_evalue`, `i_evalue` | HMMER's sequence and domain scores, with `-Z` set to the whole database |
| `hmm_from`, `hmm_to` | the stretch of the model that is aligned |
| `ali_from`, `ali_to`, `env_from`, `env_to` | the alignment and envelope on the ORF, in residues |
| `cigar` | the alignment against the model: `M` match, `I` residues the model lacks, `D` model positions the ORF lacks |
| `residues` | the aligned residues, gaps removed |
| `pp` | HMMER's posterior probability characters, one per CIGAR operation |

With `pfam_search_engine = hmmsearch`, the default, no alignments are published: `hmmsearch` runs with `--noali` and only its domain table is kept, which has the coordinates but no alignment.

```
function-summary
└── pfam
    ├── ERZ12345_pfam.txt.gz
    ├── ERZ12345_pfam.stats.json
    ├── ERZ12345_pfam_orf_filter.stats.json
    └── ERZ12345_pfam_alignments.parquet
```

## Top-level summary output files

### MultiQC

This folder contains an aggregation of all file contained in the MultiQC reports for each run. As such, it is a top-level aggregation of all MultiQC reports in the pipeline run. The interactive report is found in `study_multiqc_report.html`.

### Output status

#### QC failed runs

The pipeline runs some check on every input run following QC, decontamination and analysis. For any run failing one of these checks, the ID and reason for failure is added to a top-level report (`qc_failed_runs.csv`). The reasons for failure are:
* `no_reads`: if there are no reads following QC and decontamination
* `all_empty_results`: if there are no results generated
* `some_empty_results`: if at least one of the results files are missing

#### QC passed runs

Similarly to `qc_failed_runs.csv`, for all runs that pass the checks, the ID and status are added to `qc_passed_runs.csv`. There is only one possible status:
* `all_results`
